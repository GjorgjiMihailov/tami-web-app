# Увозни трошоци → магацинска вредност (landed cost) на влезна фактура

## Контекст и стандард

МСС 2 / МСФИ за МСЕ (важи и во Македонија) бара залихите да се вреднуваат по
набавна цена, а „набавна цена" ги опфаќа **трошоците на набавка плус сите
трошоци директно поврзани со доведување на стоката до моменталната локација и
состојба** — превоз, шпедиција, царина. Данок на додадена вредност **не**
влегува во таа бројка кога е одбитен (се враќа преку ДДВ-04), па landed-cost
пресметката подолу го исклучува ДДВ и зема само основица/царина.

Тами веќе го пресметува просечниот трошок на залиха по пондерирана просечна
цена (`StockLevel.average_cost`, движено преку `StockMovementService`), а
екраните „Состојба" и „Вреднување на залихи" веќе ја прикажуваат вредноста —
ништо од тоа не се менува. Она што недостасува е **влезот**: денес
`PurchaseInvoiceService::confirm()` секогаш го зема чистиот фактурен износ
(`PurchaseInvoiceLine::effectiveUnitPrice()`) како единечна цена при прием на
залиха. Увозните трошоци (превоз, шпедиција, царина) немаат каде да влезат, па
магацинската вредност на увезена стока излегува пониска од реалната.

## Цел / опсег

На влезна фактура со увезени артикли, сметководителот штиклира „Фактура од
увоз" и внесува увозни трошоци и царина; тие автоматски се распределуваат на
ставките пропорционално по вредност, па на залиха влегува **магацинската**
(landed) цена наместо голата фактурна цена.

**Во опсег:**
- Чекбокс „Фактура од увоз" на влезна фактура, видлив само кога фактурата има
  барем една ставка-артикл (не услуга).
- Посебен „Увоз" сектор (визуелно одвоен, како е-Фактура боксот) со ЕЦД број,
  датум на увоз, валута и курс — курсот се повлекува автоматски од НБРМ за
  датумот на увоз (постоечкиот `ExchangeRateService`), рачно променлив.
- Таб „Увозни трошоци" — слободни редови (добавувач/шпедитер, нивна фактура,
  износ во девизи, основица во денари, ДДВ, со ДДВ).
- Таб „Распределба по царински тарифи" — слободни редови (тарифски број како
  текст, износ во девизи, царина во денари, ДДВ во денари). Тарифскиот број
  **не** се проверува против официјална номенклатура — слободен текст.
- Автоматска пропорционална распределба (по вредност на ставката) на вкупните
  увозни трошоци (основица + царина, **без** ДДВ) на сите ставки-артикли од
  таа фактура.
- Преглед по ставка: Набавна вредност (фактурна) / Увоз (удел) / Магацинска
  вредност / Продажна цена.
- При потврда на фактурата, залихата прима по **магацинска** (landed)
  единична цена, не по фактурна.

**Надвор од опсег (свесно одложено):**
- **Без книжење во главната книга за увозните трошоци.** Сметката 660
  (залиха) при потврда и натаму се задолжува само со фактурниот износ, исто
  како денес. Магацинската вредност ќе биде повисока од книгата на 660 за
  сумата на увозните трошоци — реална, документирана разлика до одлука за
  целосна ДДВ+книжење структура (истата одлучена одложена сесија што веќе важи
  за „Други трошоци").
- Без проверка на царински тарифен број против вистинска номенклатура/база.
- Без автоматско читање увозни документи (скенирање важи само за самата
  фактура, не за ЕЦД/шпедитерски фактури).
- Важи само за влезни фактури — не за профактури, не за излезни.

## Податочен модел

Три нови миграции, следејќи го постоечкиот стил (`unique()` имиња рачно
кратки, `decimal` со експлицитна прецизност):

**1. На `purchase_invoices`:**
```
is_import                     boolean, default false
customs_declaration_number    string, nullable   // ЕЦД број
import_date                   date, nullable
import_currency_code          string(3), nullable
import_exchange_rate          decimal(12,4), nullable
```

**2. Нова табела `purchase_invoice_import_costs`** (таб „Увозни трошоци"):
```
id
purchase_invoice_id  FK → purchase_invoices, cascade on delete
payee_name           string                 // Фирма/шпедитер
reference_number     string, nullable       // нивна фактура
foreign_amount       decimal(14,2), nullable
base_amount          decimal(14,2)          // Основица (ден.) — влегува во распределбата
vat_amount           decimal(14,2), default 0
sort_order           unsignedInteger, default 0
timestamps
```

**3. Нова табела `purchase_invoice_tariff_lines`** (таб „По царински тарифи"):
```
id
purchase_invoice_id  FK → purchase_invoices, cascade on delete
tariff_code          string                 // слободен текст
foreign_amount        decimal(14,2), nullable
customs_duty          decimal(14,2)          // Царина (ден.) — влегува во распределбата
vat_amount             decimal(14,2), default 0
sort_order             unsignedInteger, default 0
timestamps
```

Модели `PurchaseInvoiceImportCost` и `PurchaseInvoiceTariffLine`, секој
`belongsTo(PurchaseInvoice::class)`; на `PurchaseInvoice` се додаваат
релациите `importCosts()` и `tariffLines()` (`hasMany`, по `sort_order`).

## Пресметка (landed cost)

Нова чиста, безсостојбена класа `App\Services\Inventory\LandedCostAllocator`
(или слична), со еден метод:

```php
/** @return array<int, string> purchase_invoice_line_id => landed unit cost */
public function allocate(PurchaseInvoice $invoice): array
```

Логика:
1. Земи ги само ставките-артикли (производ, не услуга — исто правило како
   `PurchaseInvoiceService::movesStock()`).
2. Вкупно за распределба = SUM(`import_costs.base_amount`) +
   SUM(`tariff_lines.customs_duty`) — **без** ДДВ колоните (тие се само
   информативни, за усогласување со фактурата на шпедитерот/царина).
3. Секоја ставка добива удел пропорционален на нејзината нето вредност
   (`lineTotal()`) спрема вкупната нето вредност на сите ставки-артикли на
   фактурата; заокружување bcmath на 2 децимали, а остатокот од
   заокружувањето (ако SUM(удели) ≠ вкупно за распределба поради заокружување)
   оди на **последната** ставка — истиот принцип веќе применет кај девизната
   фактура.
4. Магацинска вредност на ставка = `lineTotal()` + удел.
5. Магацинска единична цена = Магацинска вредност ÷ количина, bcmath
   half-up на 4 децимали (истата прецизност/заокружување како
   `StockMovementService::bcDivRoundHalfUp`, COST_SCALE=4).
6. Ако фактурата не е увозна или нема увозни трошоци/царина, методот враќа
   празен низа/landed = фактурна цена — нулта влијание на постоечко однесување.

Оваа класа е **единствениот извор на вистина** и се користи и во прегледот
(форма) и при потврда (сервис) — нема засебно „зачувана" landed цена по ставка
што може да застари; секогаш свежо пресметана од тековните увозни редови.

## Интеграција

**`PurchaseInvoiceForm` (Livewire):**
- Нови јавни својства: `isImport`, `customsDeclarationNumber`, `importDate`,
  `importCurrencyCode`, `importExchangeRate`, `importCosts[]`,
  `tariffLines[]`, `showLandedPreview` (bool, за откривање на прегледот по
  „Пресметај").
- Копчето „Пресметај" само го открива прегледниот дел (`showLandedPreview =
  true`); самата бројка секогаш се пресметува во `render()` преку
  `LandedCostAllocator` од тековните редови во меморија (без зачувување), па
  прегледот останува жив и по откривањето.
- Копче „↻ НБРМ" повикува `ExchangeRateService::getRate($currency,
  Carbon::parse($importDate))` и го полни `importExchangeRate` — истиот
  образец веќе употребен во `JournalEntryForm::fetchRate()`.
- `persist()` го зачувува `is_import` + ЕЦД/датум/валута/курс на фактурата, ги
  брише и презапишува `importCosts`/`tariffLines` редовите (исто како што веќе
  прави со `lines()->delete()` + recreate).
- Секторот „Увоз" е целосно скриен (Alpine `x-show`) кога `isImport` е лажно;
  чекбоксот самиот е видлив само кога постои барем една ставка-артикл.

**`PurchaseInvoiceService::confirm()`:**
- Пред циклусот по ставки, ако `$invoice->is_import`, пресметај
  `$landedCosts = $allocator->allocate($invoice)` еднаш.
- На местото каде денес оди `$line->effectiveUnitPrice()` во повикот кон
  `stockMovementService->receipt()`, користи
  `$landedCosts[$line->id] ?? $line->effectiveUnitPrice()`.
- Книжењето (JournalEntry, сметка 660, ДДВ) **останува непроменето** — сѐ уште
  се задолжува само со фактурниот износ (свесна одлука, видено погоре).

**Нема промени** во `StockLevelQuery`, „Состојба" и „Вреднување на залихи" —
тие веќе читаат `StockLevel.average_cost`, кое автоматски ја отсликува landed
цената штом влезе преку `receipt()`.

## Изглед (UI)

Потврдено со визуелен мокап (`import-section-v4.html`, порамнето): чекбокс
„Фактура од увоз" во сопствена сива рамка (сличен стил на другите штиклиња на
формата); под него, кога е штиклирано, портокалова рамка со лев акцент
(border-left 4px #ff6600) насловена „Увоз" со беличка „ЕЦД" — истиот визуелен
јазик како постоечкиот е-Фактура статус-бокс, видно одвоен од остатокот на
формата.

Внатре: ред со ЕЦД број / Датум на увоз / Валута / Курс (+ копче „↻ НБРМ"),
два таба („Увозни трошоци" / „Распределба по царински тарифи") со табели што
хоризонтално скролаат ако не се собираат, лента со тотали (Трошоци / Царина /
За распределба) и копче „Пресметај магацинска вредност". По кликот, под
секторот се прикажува табела по ставка: Артикл, Кол., Набавна (фактурна),
Увоз (удел), **Магацинска вредност** (истакната во портокалово), Продажна.

## Тестирање

- `LandedCostAllocator`: unit-тестови за распределба (две ставки различна
  вредност, заокружување, нула увозни трошоци → landed = фактурна, фактура без
  артикли-ставки → празен резултат).
- `PurchaseInvoiceService::confirm()`: feature-тест дека увозна фактура со
  трошоци создава `StockMovement` со `unit_cost` = landed, а не фактурна; дека
  книжењето (660) сепак е на фактурниот износ (регресија на постоечкото
  однесување).
- `PurchaseInvoiceForm`: тест дека чекбоксот е скриен без ставки-артикли, дека
  „↻ НБРМ" го полни курсот, дека прегледот по ставка се менува веднаш штом се
  смени трошочен ред (без повторно „Пресметај").
- Регресија: постоечки влезни фактури (без штиклирано „Фактура од увоз")
  остануваат бит-за-бит исти — `is_import` default false значи
  `LandedCostAllocator` враќа landed = фактурна насекаде.

## Познати ограничувања (намерно)

- Магацинската вредност ќе биде повисока од состојбата на сметка 660 во
  главната книга за сумата на увозните трошоци, сѐ додека не се одлучи
  целосната ДДВ+книжење структура (поврзано со истата отворена точка за
  „Други трошоци").
- Царинскиот тарифен број е слободен текст, без проверка.
- Увозен ДДВ (на трошочните и тарифните редови) е само информативен приказ,
  не влегува во распределбата — претпоставува дека фирмата е ДДВ-обврзник и
  го враќа ДДВ-то преку ДДВ-04. Ако некогаш се јави увозен клиент кој НЕ е
  ДДВ-обврзник, оваа претпоставка треба да се преиспита (ДДВ тогаш би требало
  да се капитализира).
