# Фаза 8в: Прифаќање на влезни (набавни) е-фактури — дизајн

**Датум:** 2026-08-06
**Статус:** Одобрено од корисникот, чека спецификациски self-review

## Контекст и цел

Фаза 8б (потпишување, испраќање, статус, официјален ПДФ за **излезни** продажни е-фактури) е целосно завршена и live-verified против `efakturatest.ujp.gov.mk`. Ова е Фаза 8в — последниот дел од Фаза 8 поделбата (види `docs/superpowers/specs/2026-07-31-efaktura-integration-design.md`): откривање и прифаќање/одбивање на **влезни** (набавни) е-фактури од добавувачи.

**Клучно архитектурно ограничување, наследено од 8б:** секоја операција што бара JWS-потпишување (вклучувајќи откривање нови документи, преземање payload/статус, прифати/одбиј, преземање ПДФ) минува низ browser → локален .NET signing bridge → физички SafeNet USB хардверски токен → PIN-попап. Ова значи дека **ниту еден дел од овој тек не може да биде автоматска/позадинска (cron) задача** — сѐ мора да биде рачно активирано од корисник со приклучен токен, исто како „Освежи статуси" во 8б. Оригиналниот Фаза 8 дизајн-документ спомнуваше „background job на интервал" — тоа е застарена претпоставка од пред 8б да се изгради, овој документ ја заменува.

**Опфат-ограничување, наследено од 8б:** само `own`-mode компании (компанија со сопствен регистриран токен) го користат овој тек. `firm`-mode резолуција (фирмата потпишува во име на клиент) сѐ уште не е дефинирана никаде во моделот (иста граница како 8б-ii-от send endpoint) и останува надвор од опфатот.

## Архитектура: посебна „inbox" табела

Разгледани два пристапа за складирање на откриените влезни документи:

- **Опција А (избрана):** посебна табела `incoming_efaktura_documents` — секој откриен документ добива запис веднаш штом е откриен (со целосен суров JSON payload). `PurchaseInvoice` запис се создава **само** откако сметководителот експлицитно ќе кликне „Прифати". Одбиените документи остануваат само во оваа табела, никогаш не создаваат `PurchaseInvoice`.
- **Опција Б (отфрлена):** веднаш креирање `PurchaseInvoice` при откривање, со нов „pending" статус. Отфрлена бидејќи: одбиените фактури би барале бришење или „мртви" редови во главната книговодствена табела; нема природно место за целосниот суров JSON payload; ризик од судир со постојниот `purchase_invoices` unique constraint (`company_id`+`partner_id`+`supplier_invoice_number`) пред да се провери за дупликати; конфликтира со целта партнер/ставки да не се создаваат/менуваат во книговодството пред експлицитна човечка одлука.

Опција А е избрана — чист раздел помеѓу „видовме документ од УЈП" и „ова е вистинска книговодствена трансакција".

## Модел на податоци

Нова табела `incoming_efaktura_documents`:

| Колона | Тип | Опис |
|---|---|---|
| `id` | | |
| `company_id` | FK → companies | |
| `euid` | string | УЈП идентификатор на документот, unique по company_id |
| `status_code` / `status_name` | string | Тековен статус кај УЈП (пр. „01"/„Испратена (Нова)") |
| `doc_number` | string | `docNumber` од payload-от (за приказ во листата) |
| `doc_date` | date | `docDate` од payload-от |
| `seller_name` | string | Име на добавувач од payload-от (за приказ пред да постои Partner) |
| `seller_tax_id` | string | ЕДБ на добавувач, нормализирано (без MK/МК префикс) |
| `total_amount` | decimal(15,2) | Вкупен износ од `docTotals` (за приказ во листата) |
| `payload_json` | json/text | Целосен суров JSON од `payload` endpoint-от, чуван засекогаш за аудит/ре-обработка |
| `discovered_at` | timestamp | Кога прв пат откриено |
| `decision` | nullable string enum(`accepted`,`rejected`) | null = сѐ уште неодлучено |
| `decided_at` | nullable timestamp | |
| `decided_by` | nullable FK → users | |
| `reject_reason_code` | nullable string | O-1..O-7 шифрарник |
| `reject_comment` | nullable string | Слободен текст, задолжителен само за О-7 |
| `purchase_invoice_id` | nullable FK → purchase_invoices | Пополнето само по Прифати |
| `efaktura_pdf_path` | nullable string | Кеширана патека до преземениот официјален ПДФ (по прв successful fetch) |

Нова колона на `companies`: `efaktura_purchase_last_checked_at` (nullable timestamp) — горна граница на периодот проверен во претходното „Провери за нови фактури"; null значи никогаш не е проверено (првото проверување зема период од почетокот на годината до сега).

Нова колона на `purchase_invoice_lines`: `needs_review` (boolean, default false) — се поставува на `true` за линии чиј УЈП даночен индикатор не мапира на постојниот 4-категориски `vat_treatment` модел (види ДДВ-мапирање подолу).

## Тек на откривање

Нов екран **„Влезни е-Фактури"** во Invoicing модулот. Копче **„Провери за нови фактури"**:

1. За тековната компанија (само ако е `own`-mode со активни е-Фактура акредитиви): потпишува и повикува `POST /einvoice_api/api/v1/documents/purchase-invoice/ids` за период `efaktura_purchase_last_checked_at` (или почеток на тековната година, ако null) до денес.
2. За секој вратен EUID кој сѐ уште го нема во `incoming_efaktura_documents` за таа компанија: повикува `payload` (целосен JSON) + `current-status`, создава нов запис.
3. За постоечки записи со `decision = null`: истиот повик по потреба ги освежува `status_code`/`status_name` (на пр. ако статусот се променил преку УЈП порталот директно), без дополнително потпишување.
4. Ажурира `companies.efaktura_purchase_last_checked_at = сега`.
5. Прикажува резиме: „Пронајдени X нови фактури."

Овој тек го користи истиот генерализиран `EfakturaJwsService::buildSigningInputForPayload()` шаблон веќе изграден во 8б-статус-фичерот (потпишува мал JSON `{requestTimestamp, dateFrom, dateTo}`), плус нов метод што секвенцијално ги презема payload+status за секој нов EUID.

## Тек на Прифати / Одбиј

За секој запис со `decision = null`: копчиња **Прифати** / **Одбиј**.

**Прифати:**
1. Потпишува и повикува `accept-reject` (`{requestTimestamp, euid, isAccepted: true}`).
2. При успех, мапира `payload_json` → нов `PurchaseInvoice` (статус `draft`, идентично на рачно внесена влезна фактура):
   - **Партнер**: бара `Partner` по нормализиран `tax_id`; ако не постои, автоматски создава нов `Partner` со име/адреса од payload-от (без дополнителен чекор за потврда — конзистентно со 8б-ii-от нема-повторна-потврда пристап за партнер-податоци).
   - **Ставки**: секој `docItems[]` елемент → `PurchaseInvoiceLine` со `item_id = null`, `account_id = null` (сметководителот ги пополнува рачно при преглед на драфтот), `description` = слободен текст од payload-от, `quantity`/`unit_price` директно мапирани.
   - **ДДВ-мапирање** (реверзно од 8б-ината табела): DDV-A→18%/standard, DDV-V→10%/standard, DDV-B→5%/standard, DDV-G→0%/standard, DDV-7-I→export, DDV-8→exempt_with_credit, DDV-9→exempt_without_credit. Секоја непозната/неподдржана шифра (пр. член 32/32-а reverse-charge кодови) → линијата се создава со `vat_rate = 0`, `needs_review = true`; фактурата сепак се прифаќа кај УЈП и драфтот се создава нормално, само со видлива предупредувачка порака во UI за таа линија.
   - `docPayment` игнориран — плаќањата остануваат целосно рачни, како и досега.
   - `supplier_invoice_number` = `docNumber` од payload-от.
3. Зачувува `purchase_invoice_id`, `decision = accepted`, `decided_at`, `decided_by` во `incoming_efaktura_documents`.
4. Сметководителот продолжува на постоечкиот `PurchaseInvoiceForm` (draft статус) за преглед/корекција (вклучувајќи ги `needs_review` линиите) и рачно **Потврди** (GL-постирање) — целосно непроменет постоечки тек.

**Одбиј:**
1. Мал модал: dropdown со причина од шифрарникот (O-1..O-7, О-7 бара слободен текстуален коментар).
2. Потпишува и повикува `accept-reject` (`{requestTimestamp, euid, isAccepted: false, rejectReasonCode, comment}`).
3. Зачувува `decision = rejected`, `reject_reason_code`, `reject_comment`, `decided_at`, `decided_by`. Нема креирање на `PurchaseInvoice`.

## УИ екран „Влезни е-Фактури"

Livewire компонента, стилски конзистентна со `SalesInvoiceIndex`-от статус-колона од 8б. Колони: Добавувач (со ЕДБ), Датум, Износ, Статус кај УЈП, Наша одлука (Неодлучено/Прифатена/Одбиена). Копчиња по ред:
- **Прифати** / **Одбиј** — само за `decision = null` записи
- **Прегледај фактура** — линк до `PurchaseInvoiceShow`, само за прифатени
- **Преземи ПДФ** — само за прифатени, повикува нов `purchase-invoice/pdf` endpoint (истиот образец како `EfakturaPdfController` од 8б: потпишува, презема, кешира во `efaktura_pdf_path`, серви од кешот при повторен клик)
- **Одбиена** статус-ознака (без копчиња) за веќе одбиени записи

Врв на екранот: копче „Провери за нови фактури" + текст „Последна проверка: {timestamp}".

## Промени во моделот (резиме)

- нова табела `incoming_efaktura_documents` (колони: види погоре)
- `companies`: нова колона `efaktura_purchase_last_checked_at`
- `purchase_invoice_lines`: нова колона `needs_review` (boolean, default false)

## Опфат — надвор од овој дизајн

- `firm`-mode компании (исто ограничување како 8б-ii-от send endpoint)
- Автоматско поврзување на `docItems` со постоечки `Item` записи — секогаш слободен текст (идно подобрување)
- Следење промени по прифаќање преку УЈП `changes` endpoint
- Позадинска/cron автоматизација на откривањето — секогаш рачно копче, поради хардверски-токен ограничувањето
- Валидација дали `standard`+нестандардна стапка (пр. 7%) паѓа во истата 500-грешка класа веќе позната од 8б — истиот општ `needs_review` механизам ја покрива оваа само делумно (мапата гледа само на познати шифри, не на произволна процентна вредност); ако се јави, третирај го исто како непозната шифра

## Технички ризик

Точните request/response shapes на `purchase-invoice/ids`, `payload`, `accept-reject` и `purchase-invoice/pdf` endpoints се земени од `efakturawiki.ujp.gov.mk` документацијата captured во 8б-статус-сесијата, но **не се live-тестирани**. По аналогија со 8б-ината и статус+ПДФ-фичерот историја (415→JSON-body фикс, погрешна base-path, погрешно date-поле), реално е да се очекуваат неколку рунди на итерација при живото тестирање (Task за live verification во имплементацискиот план треба експлицитно да го предвиди ова, со истата дисциплина за времена debug-логика: додади, живо тестирај, отстрани во иста сесија).
