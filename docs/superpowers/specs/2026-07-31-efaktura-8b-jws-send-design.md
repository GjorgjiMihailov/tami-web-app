# Phase 8b: е-Фактура — потпишување и испраќање на продажни фактури — дизајн

**Датум:** 2026-07-31
**Статус:** Одобрено од корисникот, чека спецификациски self-review

## Контекст

Продолжение на Phase 8 (`docs/superpowers/specs/2026-07-31-efaktura-integration-design.md`), под-чекор 8b. Phase 8a (модел на акредитиви по фирма) е веќе завршена и деплоирана — сертификатот е поврзан преку таа UI, па за разлика од претпоставката при 8a-дизајнирањето, вистинско тестирање против `efakturatest.ujp.gov.mk` е сега можно од самиот почеток.

Извори: `api-documentation-public7.pdf` (целосна API спецификација), `primer_za_json_2.pdf` (реални примери на JSON payload), `sifrarnici_24042026.pdf` (шифрарници).

**Потврдени факти од официјалната документација:**
- URL за испраќање: `https://efakturatest.ujp.gov.mk/JSONReceiver/api/v1/sales-invoices/send`
- URL за read-only reference повици: `https://efakturatest.ujp.gov.mk/einvoice_api/`
- Секое барање што содржи/менува документ (испраќање, статус, преземање) бара хедерите `X-EUJP-ID`, `X-EDB`, `X-SERIAL-NUMBER`, и телото на барањето мора да е **потпишано како JWS**.
- Документацијата **никаде не ја опишува конкретната JWS-конструкција** (кои полиња одат во header, `alg`, `x5c`, редослед на base64url-енкодирање) — само го наведува фактот „signed as JWS". Ова е реален, недокументиран технички ризик, потврден со целосно читање на 32-те страници од API-документот.

## Опфат

На `SalesInvoiceShow`, за потврдена (confirmed) фактура: копче **„Испрати кон е-Фактура"**, статус-бејџ, копче „Освежи статус". Член 32/32-а сценарија остануваат надвор од опфат (веќе одлучено во design.md на Phase 8) — за таков ред, испраќањето едноставно не е достапно, со јасна порака.

## Промени во податочниот модел

**Нови структурирани адресни полиња** (реален јаз откриен при ова брејнсторминг — УЈП бара `streetAddress`/`streetNumber`/`postalCode`/`city` одделно за `seller`/`buyer`, а постоечкиот модел има само едно слободно поле `address`):
- `companies`: нови колони `street_address`, `street_number`, `postal_code`, `city` (покрај постоечкото `address`, кое си останува непроменето за сѐ друго — PDF-и, екрани). Уредување преку постоечката Company Profile („Почетна → Уреди") форма.
- `partners`: истите 4 нови колони, истата причина. Уредување преку постоечката `PartnerShow` „Уреди" форма.
- Двете полиња се пополнуваат рачно од корисникот пред прво испраќање — нема автоматска миграција/парсирање на постоечкото `address` поле (ризично, македонските адреси немаат единствен формат).

**Ново поле на фактура:**
- `sales_invoices.payment_type_code` — задолжително, шифрарник P10–P19 (Готово/Картичка/Банка/Рати/Онлајн-банка/Мобилна апликација/Без надомест/Компензација/Ваучер/Друго). Нов dropdown „Начин на плаќање" во `SalesInvoiceForm`, default `P12` (Плаќање преку банка).

**Полиња веќе додадени во Phase 8a** (без промена): `sales_invoices.efaktura_euid`, `efaktura_status_code`, `efaktura_sent_at`.

## Мапирање кон УЈП JSON

Потврдено со реални примери од `primer_za_json_2.pdf`:

| УЈП поле | Извор |

## Потпишување (JWS)

**Одобрен пристап: `web-token/jwt-framework` + `openssl_pkcs12_read()`.**

Веќе го користиме `openssl_pkcs12_read()` во Phase 8a за верификација на сертификатот при upload — истата функција го дава приватниот клуч + сертификатниот синџир во PEM, кои се подаваат на `web-token/jwt-framework` за градење вистински JWS (`alg: RS256`, `x5c` header од сертификатот). Разгледани и отфрлени алтернативи:
- **Рачна имплементација само со `openssl_sign()`** (нула нови зависности) — отфрлено: JOSE-компактната сериализација (редослед на header-полиња, точен base64url формат, `x5c` низа) има ситни детали кои лесно создаваат JWS што технички изгледа исправно, но паѓа кај строг сервер-валидатор — истиот тип ризик како dompdf-flex бубачката од Sales Invoice PDF редизајнот (изгледа точно, паѓа само во реално извршување).
- **`lcobucci/jwt`** — отфрлено: послаба нативна поддршка за `x5c`/сертификатни синџири од `web-token`.

Нов `App\Services\Efaktura\JwsSigner` (прима JSON payload + `Company` со важечки акредитиви, враќа JWS compact string) и `App\Services\Efaktura\EfakturaClient` (Laravel HTTP client; методи `sendSalesInvoice()` → `JSONReceiver/api/v1/sales-invoices/send`, `refreshStatus()` → `current-status`). Base URL конфигурабилен преку `.env` (`EFAKTURA_BASE_URL`, веќе предвидено во Phase 8 дизајнот).

## Ред на изведба: спајк пред целосен план

Бидејќи точниот JWS-формат што УЈП го прифаќа е недокументиран технички ризик, а сертификатот сега е поврзан на продукција (каде единствено постои — Клод нема SSH пристап до дроплетот), редот е:

1. **Спајк-задача** (пред `writing-plans`): мала, привремена `php artisan efaktura:spike-send {company}` команда во апликацијата — конструира еден статички тест-JSON payload, го потпишува со веќе-складираниот сертификат на дадената фирма (преку постоечкиот `Company` сертификат-вчитувачки код од Phase 8a), го испраќа кон `efakturatest` и го печати целосниот одговор. Push на `main` → auto-deploy → корисникот ја извршува командата преку SSH и го враќа одговорот (само одговорот од УЈП, никогаш сертификатот/лозинката).
2. **Ако УЈП го прифати форматот** → техничката основа е потврдена, продолжуваме со `writing-plans` за целосна имплементација (форма-полиња, копче на `SalesInvoiceShow`, статус-следење, автоматски тестови со мокирани HTTP одговори).
3. **Ако УЈП одбие** → читаме ја точната грешка, прилагодуваме (header-полиња/`x5c`/`alg`), повторуваме — можни се повеќе итерации, веќе антиципирано во Phase 8 дизајнот.

Спајк-командата е привремена и се отстранува (или се остава неактивна зад feature-флаг) откако вистинската имплементација е готова — не е дел од трајниот производствен код.

## UI тек и грешки

Веќе одобрено во Phase 8 дизајнот, без промена:
1. Копче „Испрати кон е-Фактура" на `SalesInvoiceShow` за потврдена фактура — потпишува + испраќа.
2. Успех: зачувува `efaktura_euid`, `efaktura_status_code`, `efaktura_sent_at`; статус-бејџ (Испратена/Прифатена/Одбиена/Сторнирана).
3. Копче „Освежи статус" (рачно, повикува `current-status`) — нема background job за автоматско следење во оваа фаза.
4. Неуспех (потпишување или мрежа/УЈП одбивање): јасна порака на корисникот; ГЛ-постирањето (веќе направено при „Потврди") останува непроменето — испраќањето е одвоена, неблокирачка операција.
5. Сторнирање во системот не испраќа автоматски сторно кон е-Фактура (засебно, идно рачно дејство).

## План за верификација

- Автоматски тестови (PHPUnit) покриваат: мапирањата (адреса, `payment_type_code`, vat_treatment→tax indicator, вкупни/ДДВ-групирање), JWS-конструкцијата со тест-сертификат генериран во тестот (истиот принцип како Phase 8a-та лекција — вистински генериран PKCS#12 fixture, не fake upload), `EfakturaClient` со мокирани HTTP одговори.
- Спајкот (чекор погоре) го потврдува вистинскиот формат пред планот да се напише во детали.
- По деплојот, вистинско испраќање на реална продажна фактура кон `efakturatest.ujp.gov.mk` (не само спајк-статичен payload) — краток, посебен чекор откако кодот е готов.

## Надвор од опфат (без промена од Phase 8 дизајнот)

- Автоматско поврзување на влезни ставки со постоечки `Item` записи (8c)
- Сторно-испраќање кон е-Фактура директно од постоечкото Cancel копче
- Член 32/32-а reverse-charge сценарија
- Автоматско (наместо рачно) испраќање при „Потврди" на продажна фактура
- Background job за автоматско следење статус (само рачно „Освежи статус" во оваа фаза)
